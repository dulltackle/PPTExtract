# 在项目侧建立页投影并隔离 anydoc

anydoc 0.x 会把整份 `.pptx` 转成没有页节点的扁平块序列，图片资产也不携带页归属；等待上游只会增加文本分隔符，仍不能支撑页指纹。我们因此在 anydoc 之前建立项目自有的页投影边界：按源文档的 `sldIdLst` 生成有序页清单，为选中的每一页构造隔离的单页投影并分别调用 `to_document()`。初版投影复制原始 OPC 包、只收窄演示文稿的页入口，并保守保留关系闭包，不以最小包体积为目标。

页清单记录源页引用、原始 1 基页序和隐藏标记。隐藏页也会登记，但默认不转换、不渲染、不进入策展；人工启用后才处理，并继续使用原始页序。转换和渲染共享这份页清单、选择结果与页映射，但渲染器不必使用 anydoc 的物理单页投影；它可以在后续验证中选择整份渲染后映射，或使用更保守的渲染投影。

anydoc 只存在于转换适配层。适配层立即把 `to_document()` 的结果归一化为项目内部页内容模型，anydoc 对象不得进入业务层。依赖更新策略跟随最新版，但每次构建必须精确锁定实际解析版本；升级只有在页隔离、块类型、表格网格、演讲者备注、图片引用与字节、占位符过滤及错误处理等契约测试通过后才能合入或部署。

页指纹使用带 `fingerprint_version` 的规范输入。适配层将页标题、正文、表格、图片 alt text 与演讲者备注等来源内容确定性序列化，再按图片引用的出现顺序和重复次数纳入对应图片字节的哈希。转换器升级若改变了规范内容语义，必须提升指纹版本并显式处理既有审核，不能静默继承。

## Considered Options

等待或推动 anydoc 上游不能解决图片归属且时间不可控；维护 fork 会把一个快速变化的 0.x 转换器变成长期负担；改用 markitdown 会丢失结构化表格、可靠的备注区分和占位符噪声过滤；直接使用 python-pptx 则需要重写 anydoc 已具备的文本级联与 DrawingML 处理。强制渲染与转换使用同一个单页包也被否决，因为这会在渲染方案验证前锁死动态页码、性能和保真度取舍。

## Consequences

页投影和 anydoc 适配层成为所有页级处理的入口，后续的页身份、审核继承和摄取幂等都可建立在可靠的页归属上。代价是逐页转换与 OPC 投影的额外开销，并需要用代表性夹具持续验证关系完整性、相邻页隔离、隐藏页、跨页复用图片以及母版、版式、图表和备注等边界场景。
